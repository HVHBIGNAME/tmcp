# Диагностика

## В интерфейсе нет внешней ссылки

`127.0.0.1` — адрес локального сервера. Пока Cloudflare ещё подключается, поле внешнего адреса пустое, копирование недоступно. Панель обновляет состояние автоматически независимо от настроек журнала.

```sh
tmcp status
tmcp logs
```

Проверьте доступность сети и `cloudflared`. Для named tunnel проверьте домен, connector token и сервис `http://127.0.0.1:18787` в Cloudflare.

### Соединения зарегистрированы, но внешний адрес отвечает 502

На главной странице показаны число зарегистрированных соединений, наблюдаемый протокол и ошибки передачи запросов текущего процесса cloudflared. «Обрыв управляющего потока» относится к соединению с Cloudflare; «локальный сервис недоступен туннелю» — к origin. Это классификация сообщений журнала, а не проверка доступности сайта или точное число уникальных запросов. Нажмите «Проверить доступность» и сопоставьте время ошибки с `server.log`.

Счётчики сбрасываются при создании нового процесса туннеля. Одиночная ошибка запроса не перезапускает туннель, если другие соединения остаются зарегистрированными. Адреса запросов и их параметры в диагностическую сводку не включаются.

## Notion сообщает «MCP tool discovery failed»

- Сравните адрес в Notion с `tmcp url`.
- Quick Tunnel мог получить другое имя после перезапуска. Для неизменной ссылки используйте свой домен.
- Проверьте, что токен интеграции активен, не истёк и разрешает нужные инструменты.
- Кнопка «Проверить доступность» проверяет HTTP-ответ сервера через внешний туннель; это не проверка настроек авторизации конкретного клиента.

Ошибка обнаружения инструментов сама по себе не доказывает потерю токена. Не заменяйте ключи без необходимости.

## Сервер пропал после закрытия окна

Крестик нового приложения прячет окно в трей. «Остановить сервер и выйти» и `tmcp stop` действительно останавливают сервер. Работа продолжается только пока компьютер включён и не спит.

Фоновый наблюдатель находится в `dist/src/daemon.js`. Он запускает сервер после завершения процесса. Потеря Cloudflare-туннеля обрабатывается отдельно и не должна останавливать уже запущенные команды.

## Telegram не подключается

1. Сохраните токен бота и числовой ID чата.
2. Напишите боту `/start`.
3. Нажмите «Проверить».

`Unauthorized` означает неверный токен. `Conflict` часто означает, что этот же бот уже опрашивается другим процессом или использует webhook. Для TMCP нужен один polling-процесс на токен. TMCP не удаляет webhook автоматически.

## Интерфейс не открылся

Windows GUI использует Microsoft Edge WebView2 Runtime. Установщик проверяет его наличие. При ошибке запуска панель показывает собственный экран восстановления, а детали записывает в `.mcp-tunnel/ui-error.log`.

Для сборки из исходников нужен .NET Desktop Runtime 8. Globalization включена; русская раскладка поддерживается без отключения сообщений ввода Windows.

Панель открывается через `PcMcp.exe`, использует локальные ресурсы WebView2 и IPC. Проверьте `tmcp status` под тем же пользователем ОС. Закрытый IPC недоступен из обычного браузера; на Linux/macOS используйте терминальную панель `tmcp`.

## Автозапуск на Linux недоступен

Проверьте `systemctl --user status`. Контейнеры, некоторые SSH-сессии и минимальные дистрибутивы не предоставляют пользовательский systemd. В такой среде используйте менеджер процессов хоста/контейнера.

На сервере с systemd работа до входа пользователя требует lingering. Команды установки сами по себе его не включают.

## Установщик обновления не сообщил о готовности

Начиная с 2.2.1 ожидание помощника допускает 45 секунд. В сообщении различаются досрочный выход с кодом ошибки и timeout; добавляется последний доступный этап. `verifying-download` включает повторную проверку SHA-256, а `waiting-for-application-exit` означает готовность к остановке старого приложения.

Краткая диагностика сохраняется в `.updates/last-installer-error.json` внутри каталога установки даже после удаления неудачного скачивания. В активном каталоге `.updates/<id>/installer-state.json` виден текущий этап. Ошибки Windows-оболочки дополнительно записываются в `.mcp-tunnel/ui-error.log`.

Отключение автоматических обновлений не удаляет EXE, уже используемый установщиком. Непосредственно перед остановкой приложения режим обслуживания продлевается и занятость проверяется повторно. Эти меры и новые журналы не устанавливают задним числом причину единичного timeout в 2.2.0.

## Где журналы

| Файл                       | Содержимое                         |
| -------------------------- | ---------------------------------- |
| `.mcp-tunnel/server.log`   | Сервер, Cloudflare, MCP-шлюз       |
| `.mcp-tunnel/daemon.log`   | Запуск и восстановление процесса   |
| `.mcp-tunnel/ui-error.log` | Ошибки Windows-оболочки            |
| `.mcp-tunnel/audit.log`    | Выполненные и отклонённые действия |

Для issue приложите версию, ОС, тип туннеля и соответствующий фрагмент журнала. Перед публикацией уберите приватные пути, содержимое команд и секреты. Файлы `.env` и `settings.json` прикладывать не нужно.
